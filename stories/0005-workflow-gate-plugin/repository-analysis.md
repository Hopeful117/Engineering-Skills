# Repository Analysis — Story 0005: Workflow Gate Plugin

## 1. Story Understanding

### Objective
Implement an OpenClaw plugin that serves as the deterministic controller of the Engineering Story workflow state, enforcing Human Approval Gates through OpenClaw's native `requireApproval` mechanism.

### Key Insight
The plugin IS the Workflow State Controller. There is no separate bash script. All state mutations flow through the plugin's custom tools. The LLM never directly modifies state.

## 3. Architecture Analysis

### 3.1 State Machine

**States (11 persisted):**
```
STORY_CREATED
ANALYSIS_IN_PROGRESS
WAITING_FOR_ANALYSIS_APPROVAL
PLAN_IN_PROGRESS
WAITING_FOR_PLAN_APPROVAL
IMPLEMENTATION_IN_PROGRESS
CODE_REVIEW_IN_PROGRESS
WAITING_FOR_REVIEW_APPROVAL
REPORT_IN_PROGRESS
WORKFLOW_COMPLETED
BLOCKED
```

**Transitions (15):**
| From | To | Trigger | Guard |
|---|---|---|---|
| STORY_CREATED | ANALYSIS_IN_PROGRESS | `complete_stage` | stage == "created" |
| ANALYSIS_IN_PROGRESS | WAITING_FOR_ANALYSIS_APPROVAL | `complete_stage` | stage == "analysis" |
| WAITING_FOR_ANALYSIS_APPROVAL | PLAN_IN_PROGRESS | `request_approval` | hash verified |
| PLAN_IN_PROGRESS | WAITING_FOR_PLAN_APPROVAL | `complete_stage` | stage == "plan" |
| WAITING_FOR_PLAN_APPROVAL | IMPLEMENTATION_IN_PROGRESS | `request_approval` | hash verified |
| IMPLEMENTATION_IN_PROGRESS | CODE_REVIEW_IN_PROGRESS | `complete_stage` | stage == "implementation" |
| CODE_REVIEW_IN_PROGRESS | WAITING_FOR_REVIEW_APPROVAL | `complete_stage` | stage == "review" |
| WAITING_FOR_REVIEW_APPROVAL | REPORT_IN_PROGRESS | `request_approval` | hash verified |
| REPORT_IN_PROGRESS | WORKFLOW_COMPLETED | `complete_stage` | stage == "report" |
| Any | BLOCKED | `block` | reason provided |
| BLOCKED | Previous | `unblock` | — |

### 3.2 Custom Tools

| Tool | Purpose | Parameters | Mutates State |
|---|---|---|---|
| `workflow_gate_status` | Read current state | `storyId` | No |
| `workflow_gate_can_enter` | Check if stage can be entered | `storyId`, `stage` | No |
| `workflow_gate_complete_stage` | Mark stage as complete | `storyId`, `stage`, `artifactPath` | Yes |
| `workflow_gate_request_approval` | Request human approval for pending gate | `storyId` | Yes (after approval) |
| `workflow_gate_block` | Block workflow | `storyId`, `reason` | Yes |

### 3.3 Trust Boundary

```
LLM calls workflow_gate_complete_stage(storyId, stage, artifactPath)
  → Plugin computes hash, stores in state, transitions to WAITING_FOR_*

LLM calls workflow_gate_request_approval(storyId)
  → Plugin reads state, verifies gate is pending
  → Plugin returns requireApproval payload
  → OpenClaw Gateway pauses execution
  → Human sees approval request
  → Human clicks "Allow once" or "Deny"
  → If "Allow once": plugin verifies hash, executes transition
  → If "Deny": no transition, state unchanged
```

### 3.4 Hash Verification

1. **At `complete_stage`**: Plugin computes SHA-256 of artifact, stores hash in state.
2. **At `request_approval`**: Plugin presents hash in approval request.
3. **At approval resolution**: Plugin re-computes hash, verifies it matches stored hash.
4. **At `can-enter` for dependent stages**: Plugin verifies hash of approved artifact hasn't changed.

### 3.5 State Storage

State is stored in `api.session.state` under key `workflow-gate`:

```typescript
interface WorkflowState {
  storyId: string;
  currentState: WorkflowStateName;
  history: WorkflowEvent[];
  approvals: Record<string, ApprovalRecord>;
  blocks: BlockRecord[];
}

interface ApprovalRecord {
  stage: string;
  approvedAt: string;
  artifactHash: string;
  artifactPath: string;
}

interface WorkflowEvent {
  type: string;
  from: string;
  to: string;
  timestamp: string;
  artifactPath?: string;
  artifactHash?: string;
}
```

export default defineToolPlugin({
  id: "workflow-gate",
  name: "Workflow Gate",
  tools: (tool) => [
    tool({
      name: "workflow_gate_request_approval",
      description: "Request human approval for a workflow gate",
      parameters: Type.Object({
        storyId: Type.String({ description: "Story ID" }),
      }),
      async execute({ storyId }, config, context) {
        // Read state, verify gate, return requireApproval

  ],
});

## 6. Risk Analysis

| Risk | Impact | Mitigation |
|---|---|---|
| Plugin SDK API changes | Tool registration fails | Pin SDK version in package.json |
| `api.session.state` unavailable | State storage fails | Check at startup, fail-closed |
| Hash collision | Incorrect verification | SHA-256 (collision-resistant) |
| Race condition on state write | State corruption | Atomic writes via session state API |
| LLM bypasses tools | State not enforced | Defense in depth in delegate-task |

2. **Tool registration with `requireApproval`**: Need to verify if `requireApproval` can be returned from `execute()` or if it requires a `before_tool_call` hook.

3. **State initialization**: How does the plugin initialize state for a new story? Does `api.session.state.get()` return null for uninitialized keys?

4. **Multiple stories in same session**: Can multiple stories have independent state in the same session, or is state session-wide?

## 8. Recommendation

**Proceed to Implementation Planning.**

The architecture is clear:
- Plugin is the sole state controller
- `api.session.state` is the authoritative storage
- Custom tools are the only API
- `requireApproval` is the trust boundary
- Hash verification ensures artifact integrity

The open questions (SDK API surface) can be resolved during implementation by inspecting the TypeScript types.
